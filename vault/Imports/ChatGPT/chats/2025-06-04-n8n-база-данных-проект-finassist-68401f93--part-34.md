### Один список или две таблицы?  
(⟶ короткий ответ сразу)  
**Практичнее оставить две таблицы** – `system_documents` и `user_documents`.  
Причины — разные режимы доступа, жизненный цикл и управление версиями.  
Ниже ⟶ подробные аргументы и как настроить векторный поиск, чтобы это не усложнило схему.

---

## Почему не объединять

| Фактор | Две таблицы  | Одна «универсальная» |
|--------|--------------|----------------------|
| **Права доступа** | легко: *system* — только админ / миграции, *user* — доступ по `telegram_id`. | нужны сложные row-level-policies (RLS) с исключениями «если is_system = true – deny update» и т. д. |
| **Жизненный цикл** | системные файлы — редко меняются, ветка деплоя;<br>пользовательские — добавляются/удаляются непрерывно. | совместная таблица быстро «разбухает» ⇒ полнотекст/вектор-индекс работает медленнее. |
| **Метаданные** | разные поля: у *system* «type, version, is_active», у *user* «telegram_id, filename». | придётся хранить много `NULL`-колонок или делать jsonb-«свалку». |
| **Бэкапы / миграции** | можно мигрировать/чистить только *system*. | придётся фильтровать по флагам. |
| **Отчётность** | выборки `COUNT(DISTINCT telegram_id)` – мгновенные. | нужно `WHERE is_system = false`. Небольшая, но постоянная оговорка. |

### Когда имеет смысл одна таблица

* **совсем маленький MVP** (10-20 документов);  
* все документы действительно однотипные, отличия только в авторе;  
* вы не планируете тонкие политики доступа.

---

## Как искать векторами, если **две** таблицы

1. **Отдельный вектор-store для системных**  
   ```yaml
   DATA_BASE_SYS   -> tableName = system_embeddings
   DATA_TOOL_SYS   -> name = "sys_docs"
   ```
2. **Текущий `DATA_BASE / DATA_TOOL`** оставляете для `embeddings` (пользовательских).

В **AI-агенте** добавьте системный «инструмент»:
```js
tools: [
  { type: "vectorStore", name: "sys_docs"     },
  { type: "vectorStore", name: "documents"    },
  … остальные …
]
```
LLM сам выберет, где искать (чаще всего – сначала в пользовательских, затем в системных).

---

## Как упростить себе жизнь

* **Общие функции для вставки**  
  ```sql
  CREATE OR REPLACE FUNCTION insert_system_doc(_title text, _content text)
  RETURNS uuid AS…
  
  CREATE OR REPLACE FUNCTION insert_user_doc(_tg_id bigint, _fn text, _cont text)
  RETURNS uuid AS…
  ```
  Их можно дёргать из n8n через «Custom query».

* **Материализованный view для «всех» документов**  
  ```sql
  CREATE MATERIALIZED VIEW all_docs AS
  SELECT 'sys'  AS origin, id, title    AS filename, content FROM system_documents
  UNION ALL
  SELECT 'user' AS origin, id, filename, content FROM user_documents;
  ```
  Если нужен «единый» поиск без переключения - индексируйте именно `all_docs`.

* **Ротация embeddings**  
  Делайте `REFRESH MATERIALIZED VIEW` раз в час кроном и переиндексируйте вектора одной командой.

---

## Что менять в n8n

1. **Пользовательская ветка**: уже пишет в `user_documents` + `embeddings`.
2. **Админ-скрипт** (один раз при деплое) грузит files → `system_documents` → `system_embeddings`.
3. В **AI-Agent prompt**:  
   > «Начни поиск в пользовательских документах. Если ответ не найден – обратись к системным».

---

### Итог

*Для MVP с реально отличающимися типами данных две таблицы + два вектор-store — самое чистое решение.*  
Если в будущем выяснится, что администрировать сложно — «склеить» всегда проще, чем «разлепить» раскатанную прод-таблицу.

## 1 ⟶ Две вектор-таблицы в Supabase / Postgres

| Назначение | Таблица с текстом | Таблица c векторами |
|------------|------------------|---------------------|
| **Cистемные** шаблоны/гайды | `system_documents` | `system_embeddings` |
| **Пользовательские** файлы | `user_documents`   | `user_embeddings`   |

> **system_embeddings / user_embeddings**  содержат: `id, document_id, embedding vector(1536)`  
> На обеих – индекс `ivfflat`.

---

## 2 ⟶ Пайплайн загрузки

| Шаг | System-loader (один раз при деплое) | User-loader (каждый документ) |
|-----|--------------------------------------|--------------------------------|
| 1.  | Читаем файл → `content`              | Telegram `download file` → `Extract from File (xxx)` |
| 2.  | `INSERT INTO system_documents …`     | `INSERT INTO user_documents …` |
| 3.  | `openai.embeddings` → вектор         | то же (асинхронно / сразу) |
| 4.  | `INSERT INTO system_embeddings`      | `INSERT INTO user_embeddings` |

В n8n это **две почти одинаковые ветки**; разница только в имени таблицы и в том, кто триггерит загрузку (скрипт-миграция / Telegram-документ).

---

## 3 ⟶ n8n-узлы для поиска

1. **DATA_BASE_USER**  
   - `@n8n/vectorStoreSupabase`  
   - `tableName = user_embeddings`  

2. **DATA_TOOL_USER**  
   - `toolVectorStore`, `name = "user_docs"`

3. **DATA_BASE_SYS**  
   - `tableName = system_embeddings`

4. **DATA_TOOL_SYS**  
   - `name = "sys_docs"`

> Оставьте оба инструмента «подключёнными» к **AI Agent** через вкладку _ai_tool / ai_vectorStore_.  
> Это не создаёт лишних вызовов; LangChain заставит модель сама решить, какой store использовать.

---

## 4 ⟶ Prompt-шаблон (одно предложение к тому, что уже есть)

Добавьте к системному промпту ровно одну фразу ⬇️  

```

```

(Этого достаточно – модель увидит, что есть ещё один инструмент.)

## 5 ⟶ Что поменять в вашем workflow

1. **Ветка сохранения**  
   - после `Merge` → `Set DocS to AI` уже есть Supabase-insert;  
   - добавьте сразу **Embeddings OpenAI** + `INSERT INTO user_embeddings`.

2. **Подключение второго хранилища**  
   - скопируйте узел `DATA BASE1 / DATA_TOOL1`;  
   - поменяйте `tableName`/`name` → `system_embeddings` / `sys_docs`;  
   - соедините их тем же способом (ai_vectorStore → AI Agent).

3. **AI Agent**  
   - в настройках «Tools» должны появиться **два** vector-store-инструмента.  
     Порядок не важен.

---

### Мини-чек-лист

- [ ] В обеих таблицах embeddings - одинаковый **`dimension = 1536`**.  
- [ ] Индексы `CREATE INDEX … USING ivfflat (embedding vector_l2_ops);`  
- [ ] В User-ветке заполняете `telegram_id`, `filename`, `content`.  
- [ ] В System-ветке достаточно `title`, `content`, `document_type`.  
- [ ] Prompt содержит правило fallback на `sys_docs`.  

С такой схемой ассистент автоматически видит:  

*— «Что в моих договорах за апрель?»* → ищет в **user_docs**.  
*— «Дай шаблон Устава ООО»* → не находит у пользователя, берёт из **sys_docs**.

Готово – можно добавлять новые системные файлы без изменения рабочего workflow.

### Как вызвать **Mistral-AI Chat Completions** через обычную **HTTP Request**-ноду в n8n  

*(подойдёт для моделей `mistral-tiny`, `mistral-small`, `mistral-medium`, `mixtral-8x7b`, …)*  

---

## 1. Получите ключ API

1. Зарегистрируйтесь / войдите на <https://console.mistral.ai>  
2. Создайте **API key** — например `mistral_live_sk_xxxxxxxxx`.

Сохраните ключ — второй раз он не покажется.

---

## 2. Создадим учётку “HTTP Request” в n8n

1. **Credentials → HTTP Basic Auth** *(или HTTP Header)*  
2. Вкладка **Headers** → *Add Header*  
   | Name | Value |
   |------|-------|
   | `Authorization` | `Bearer {{MISTRAL_API_KEY}}` |
   | `Content-Type`  | `application/json` |

> Переменную `{{MISTRAL_API_KEY}}` можно хранить в n8n > **Settings → Environment Variables**.

Сохраните под именем, например, **“Mistral API”**.

---

## 3. Настройка ноды **HTTP Request**

| Поле | Значение |
|------|----------|
| **Method** | `POST` |
| **URL** | `https://api.mistral.ai/v1/chat/completions` |
| **Authentication** | выберите созданные креды **“Mistral API”** |
| **Send Body** | `Yes` |
| **Content Type** | `JSON` |
| **Body (JSON)** | ```json { "model": "mistral-medium", "messages": [ { "role": "system", "content": "You are a helpful assistant." }, { "role": "user", "content": "Привет, что ты умеешь?" } ], "temperature": 0.7, "max_tokens": 1024 } ``` |
| **Response Format** | `JSON` |

---

## 4. (Опционально) Сформируйте body динамически

Перед HTTP-нодой вставьте **Set**:

```js
items[0].json = {
  model: "mistral-medium",
  messages: [
    { role: "system", content: "Ты FinAssist-Bot — финансовый ИИ-консультант." },
    { role: "user",   content: $json.user_message }   // из предыдущего шага
  ],
  temperature: 0.5,
  max_tokens: 512
};
return items;
```

В HTTP-ноде → *Body* → `={{ $json }}` (raw JSON из предыдущей Set-нодки).

---

## 5. Используйте ответ

Mistral вернёт:

```json
{
  "id": "chatcmpl-abcd1234",
  "object": "chat.completion",
  "created": 1719426000,
  "model": "mistral-medium",
  "choices": [
    {
      "index": 0,
      "message": { "role": "assistant", "content": "…" },
      "finish_reason": "stop"
    }
  ],
  "usage": { "prompt_tokens": 31, "completion_tokens": 98, "total_tokens": 129 }
}
```

Берём текст ответа:

```
{{ $json.choices[0].message.content }}
```

и отправляем дальше в Telegram-ноде или сохраняем в `messages`.

---

## 6. (Необязательно) несколько моделей в одном воркфлоу

Поменяйте поле `"model": "mistral-tiny"` или `"mixtral-8x7b-32kse"` — больше ничего менять не нужно.

---

### Итого

1. Создали HTTP Credentials с заголовками `Authorization: Bearer …`, `Content-Type: application/json`.  
2. HTTP Request (POST) на `https://api.mistral.ai/v1/chat/completions`.  
3. Передаём JSON-body с `model`, `messages`, `temperature`, `max_tokens`.  
4. Забираем `choices[0].message.content` — готовый ответ ассистента.  

Эти шаги полностью подключают Mistral к вашему n8n-workflow.
