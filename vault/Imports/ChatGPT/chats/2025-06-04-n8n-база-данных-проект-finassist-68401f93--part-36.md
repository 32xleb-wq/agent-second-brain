## 1  Добавляем «жёсткий» шаг Retrival → Context

1. **VectorStore (Supabase) для системных документов**  
   Вы его уже создали: `DATA BASE3` → `DATA_TOOL3` (`system_documents / system_embeddings`).

2. **Нода “Vector Store Retriever” (или обычный HTTP CALL)**  
   - input = текущий `user_message`  
   - topK = 1-3  
   - вывести именно `pageContent`/`content` системных правил.

3. **Function / Set “Build_System_Context”**  
   ```js
   const sys = items[0].json.content || items[0].json.pageContent || '';
   return [{ json: { system_instructions: sys } }];
   ```

4. **Merge** (Mode → “Combine By Index”)  
   - левый вход = результат Retriever (с `system_instructions`)  
   - правый вход = ваш объект с `user_message`.

Теперь каждый item, идущий в **AI Agent**, уже содержит поле `system_instructions`.

### Почему возникает ошибка  
`Error searching for documents: PGRST202 Could not find the function public.match_system_documents/filter…`

Supabase-векторный модуль (`vectorStoreSupabase`) от **LangChain** ожидает, что у вас есть **RPC-функция** с именем **`match_<table>_documents`** (или то, что вы указали в поле *Query name*).  
В вашей таблице `system_documents` такой функции пока нет, поэтому PostgREST не находит её и отвечает PGRST202.

### Решаем в три шага
| Шаг | Действие | Что именно делаем |
| --- | --- | --- |
| **1. Убедитесь, что колонка с вектором называется `embedding` и тип `vector`** | ```sql ALTER TABLE system_documents ADD COLUMN IF NOT EXISTS embedding vector(1536);```<br>создайте индекс:<br>```sql CREATE INDEX IF NOT EXISTS idx_sysdoc_vec ON system_documents USING ivfflat (embedding vector_l2_ops);``` |
| **2. Создаём RPC-функцию «match_system_documents»** | Выполните в SQL-редакторе Supabase:  ```sql CREATE OR REPLACE FUNCTION public.match_system_documents(  query_embedding vector,  match_count int DEFAULT 10 ) RETURNS TABLE(   id uuid,   title text,   content text,   document_type text,   is_active boolean,   similarity float ) LANGUAGE plpgsql AS $$ BEGIN   RETURN QUERY   SELECT    d.id, d.title, d.content, d.document_type, d.is_active,    1 - (d.embedding <=> query_embedding) AS similarity   FROM system_documents d   WHERE d.is_active = true   ORDER BY d.embedding <=> query_embedding   LIMIT match_count; END; $$;```  *При необходимости уберите `is_active` из фильтра.* |
| **3. Настройте ноду `DATA BASE3`** | * **Operation mode** – **Retrieve documents (as Vector Store for Chain/Tool)**  <br>* **Table name** – `system_documents`  <br>* **Query name** – `match_system_documents`  |

> После сохранения функции Supabase сам «прогреет» схем-кэш. Если ошибка PGRST202 появится сразу после создания функции – просто подождите пару секунд и повторите запрос.

### Почему возникла ошибка

```
ERROR: 54000: memory required is 61 MB, maintenance_work_mem is 32 MB
```

*При построении IVFFLAT-индекса PostgreSQL сначала читает все векторы в память, затем строит «список центроидов».  
Если объём данных > `maintenance_work_mem`, сервер прерывает операцию.*

На бесплатном/«micro»-проекте Supabase лимит `maintenance_work_mem` = **32 MB** – его нельзя поднять вручную.  
Нужно **уменьшить** память, требуемую для создания индекса.

---

## Решения

| Вариант | Что сделать | Комментарий |
|---------|-------------|-------------|
| **1. Уменьшить параметр `lists`** | ```sql ALTER TABLE system_documents ALTER COLUMN embedding TYPE vector(1536);  -- если ещё не создано\n\nCREATE INDEX IF NOT EXISTS idx_sysdoc_vec\nON system_documents USING ivfflat (embedding vector_l2_ops)\nWITH (lists = 50);          -- или 32 / 16\n``` | По умолчанию `lists = sqrt(rows)` ⇒ при 5000 векторов ≈ 70 списков и ~2 bytes × 1536 × lists памяти. Снижение `lists` в 2 раза почти вдвое уменьшает RAM, но делает поиск чуть менее точным. |
| **2. Создавать индекс «пакетно»** | 1. Создайте копию таблицы только с 1–2 тыс. строк и индекс к ней.<br>2. Вставляйте оставшиеся строки малыми партиями (`INSERT … ON CONFLICT …`).<br>3. Опционально **REINDEX** после загрузки. | Позволяет обойти единоразовый пик RAM. |
| **3. `CREATE INDEX CONCURRENTLY`** | ```sql CREATE INDEX CONCURRENTLY idx_sysdoc_vec  ON system_documents USING ivfflat (embedding vector_l2_ops) WITH (lists = 50);``` | Строит индекс кусками; пиковое потребление памяти ниже. |
| **4. Сжать таблицу** | Удалите тестовые/дублирующиеся записи → `VACUUM …`. | Меньше строк → меньше памяти. |
| **5. Обновить тариф** | На *Pro* проекты Supabase `maintenance_work_mem` повышен (обычно 64–128 MB). | Самый простой, если планируете много документов. |

### Практический минимальный пример

```sql
-- 1) Убедитесь, что есть column embedding
ALTER TABLE system_documents
ADD COLUMN IF NOT EXISTS embedding vector(1536);

-- 2) Создаём индекс с уменьшенным lists
CREATE INDEX IF NOT EXISTS idx_sysdoc_vec
ON system_documents
USING ivfflat (embedding vector_l2_ops)
WITH (lists = 32);     -- подбирайте: 16 / 32 / 48
```

> Если даже при `lists = 16` ошибка повторяется, используйте `CREATE INDEX CONCURRENTLY` или уменьшите количество строк (временная копия).

### Как починить (шаги – 1 раз в БД)

```sql
-- 1.  Увеличиваем work_mem только на время индексирования
SET LOCAL work_mem = '128MB';

-- 2.  Убеждаемся, что колонка embedding есть и её тип vector(1536)
ALTER TABLE system_documents
  ADD COLUMN IF NOT EXISTS embedding vector(1536);

-- 3.  Пересчитываем embedding   (один раз на все «старые» документы)
--    (если вы уже писали скрипт – пропустите)
UPDATE system_documents
SET    embedding = 
       (SELECT embedding                           -- Ada v2 1536-float
        FROM   match_embeddings( content ) LIMIT 1)  -- своя функция или внешняя генерация
WHERE  embedding IS NULL;

-- 4.  Создаём функцию поиска (точно так, как ждёт LangChain):
CREATE OR REPLACE FUNCTION match_system_documents(
        filter       jsonb DEFAULT '{}'::jsonb,
        match_count  int   DEFAULT 10,
        query_embedding vector
) RETURNS TABLE(id uuid, content text, metadata jsonb, distance float)
LANGUAGE plpgsql AS $$
BEGIN
  RETURN QUERY
  SELECT id,
         content,
         jsonb_build_object(
             'title', title,
             'document_type', document_type
         ) AS metadata,
         embedding <=> query_embedding AS distance
  FROM   system_documents
  WHERE  is_active = true
  ORDER  BY embedding <=> query_embedding
  LIMIT  match_count;
END;
$$;

-- 5.  Индекс для ускорения (после SET work_mem):
CREATE INDEX IF NOT EXISTS idx_sysdoc_vec
    ON system_documents
 USING ivfflat (embedding vector_l2_ops)
 WITH (lists = 100);

RESET work_mem;   -- вернули прежний лимит
```
