### Раз-за-разом: что делает каждая нода  
*(идут ровно в том порядке, как данные проходят по основной «текстовой» ветке)*  

| № | Нода (id / название) | Что делает | Главное, что выходит дальше |
|---|----------------------|------------|-----------------------------|
| 1 | **Telegram Trigger** (`tgTrigger`) | Слушает ваш бот-токен → ловит **любой апдейт** из Telegram. Когда приходит сообщение, кладёт JSON апдейта в поток. | `items[0].json = { update_id, message:{…} }` |
| 2 | **Switch Message Type** (`swType`) | Смотрит, какой контент есть внутри `message` и направляет в нужный выход.<br>• *Text* — если `message.text` существует (для MVP используем только его).<br>Другие три правила (Voice / Document / Photo) пока ничем не соединены — значит апдейты с аудио/фото просто «обрубятся», пока вы не добавите соответствующие ветки. | На первом выходе (index 0) downstream-JSON остаётся без изменений |
| 3 | **SB Upsert User** (`sbUpsertUser`) | SQL-UPsert в таблицу **users** Supabase:<br>если User уже есть → обновляет `username` и `first_name`,<br>если нет → вставляет. | ничего не меняет в потоке (`items` возвращаются как пришли) |
| 4 | **SB Save User Msg** (`sbSaveMsg`) | Вставляет строку в **chat_history** (Supabase).<br>Передаёт: `session_id`, `user_id`, `username`, `role='user'`, `content` (текст сообщения). | тот же входной JSON |
| 5 | **PG Save Mem User** (`pgSaveUser`) | Дублирует ту же строку в таблицу **memory** Postgres (role = `user`). Это «короткая память» для LLM. | тот же JSON |
| 6 | **PG Load Mem** (`pgLoad`) | SELECT 100 последних строк этой же `session_id` из памяти (Postgres), упорядоченные newest → oldest. | каждый полученный ряд идёт как отдельный `item` с полями `role`, `content` |
| 7 | **Prepare Prompt** (`fnPrompt`) | Склеивает массив `items` в один длинный string-prompt:<br>`user: привет\nassistant: …\nuser: …`<br>и кладёт его в `items[0].json.prompt`. | одно-элементный массив `{ prompt:"…" }` |
| 8 | **OpenAI Chat** (`aiChat`) | Отправляет в GPT-4o-mini:<br>• system-инструкцию (личность бота)<br>• user-сообщение = сформированный `prompt`.<br>Получает ответ в `choices[0].message.content`. | `items[0].json.choices[0].message.content` — готовый ответ |
| 9 | **SB Save Assistant** (`sbSaveAns`) | Записывает ответ в **chat_history** (Supabase) с `role='assistant'`. | JSON из OpenAI (без изменений) |
|10 | **PG Save Mem Assistant** (`pgSaveAns`) | Добавляет эту же реплику в таблицу **memory** (Postgres) с `role='assistant'`. | тот же JSON |
|11 | **Telegram Send** (`tgSend`) | Отправляет текст ответа в тот же чат / юзеру. | (конец основных данных — дальше поток можно расширять) |

#### Как обрабатываются ветки Voice / Photo / Document сейчас?
* В `Switch Message Type` правила есть, но ни один из выходов **1, 2, 3** не подключён.  
* Когда придёт, например, `message.voice`, нода переключит поток на второй выход, но там нет соединения → n8n «гасит» выполнение (данные теряются).  
* Добавьте собственные ноды (STT-распознавание, загрузку файла в Supabase Storage, генерацию превью и т.д.) и соедините нужный индекс выхода со своей цепочкой.

### Что важно помнить

1. **Credentials**  
   * `telegramApi`, `supabaseApi`, `postgres`, `openAIApi` нужно выбрать в UI (Credentials Manager).  
2. **SQL-кавычки**

### 5️⃣ Postgres — Insert Memory

Сохраняем то же самое в память:

```sql
INSERT INTO memory (session_id, role, content)

```

### 6️⃣ Postgres — Load Memory

Забираем последние 100 сообщений:

```sql
SELECT role, content
FROM memory
WHERE session_id = 'user_{{ $json.message.from.id }}'
ORDER BY id DESC
LIMIT 100;
```
